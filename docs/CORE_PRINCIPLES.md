# 핵심 원칙

## 1. 세 축의 증거를 교환하지 않는다

- 기술은 코드와 실행 결과로 판단합니다.
- 의도는 작업 당시의 프롬프트·도구 설정·검증 행동으로 판단합니다.
- 인지는 사후 Q&A에서 본인이 자기 산출물을 설명하는 능력으로 판단합니다.

문서 품질은 세 축을 연결하는 데 도움을 주지만 다른 축의 증거를 대신하지 않습니다.

## 2. 목표보다 완료 상태를 먼저 쓴다

AI에게 일을 맡길 때 objective만 주지 않습니다. 허용 범위, 알려진 계약, 비목표, 이진 수용 기준,
검증 명령, 중단 조건을 함께 제공합니다. 완료는 AI의 선언이 아니라 동일한 검증의 통과로 결정합니다.

## 3. 실패는 삭제하지 않고 다음 판단의 입력으로 만든다

검증 실패 뒤에는 원인을 수정하고 **동일한 검증**을 다시 실행합니다. 실패 이벤트는 덮어쓰지 않고
새 이벤트가 `supersedes`로 이전 결정을 잇습니다. 실패→수정→재통과가 가장 강한 의도 증거입니다.

## 4. 라스트 마일은 구조와 소유권이다

- API·Admin·Customer surface의 소유권과 진입점을 명확히 합니다.
- UI, 비즈니스 규칙, I/O, Agent 판단, 결정론적 정책을 분리합니다.
- preview와 고객 화면은 하나의 renderer 또는 rendering core를 공유합니다.
- 순수 변환은 격리해 테스트합니다.
- `index`는 public API를 보여주는 목차로 유지합니다.
- 실제 production build 산출물을 생성하고 smoke test합니다.
- 사용하지 않는 starter surface와 dependency를 제거합니다.

## 5. Agent 수는 품질이 아니다

여러 agent는 독립 실행과 상호 검증의 책임 경계가 있을 때만 사용합니다. Producer는 후보를 만들고,
Judge는 고정된 후보를 읽기 전용으로 평가합니다. Judge가 자신의 결과를 채점하거나 후보를 고치면 독립
검증이 아닙니다. 안전·스키마·권한·발행의 최종 통제는 결정론적 gate에 둡니다.

## 6. 사실 경계를 지킨다

- mock과 live를 명시적으로 구분합니다.
- reconstructed 기록은 검색과 회고용이며 당시 행동 증거가 아닙니다.
- 존재하지 않는 파일·API·실행 결과를 인용하지 않습니다.
- 비밀값과 개인정보는 코드, 프롬프트, 로그, 오류 메시지에 남기지 않습니다.

## 7. 설명할 수 없는 구현은 끝난 구현이 아니다

최종 기능 추가 전에 한 번 멈추고 다음을 말로 설명합니다.

1. 왜 이 구조를 선택했고 무엇을 기각했는가
2. 요청과 데이터가 어떤 파일을 지나가는가
3. 정상 경로와 실패 경로가 어떻게 다른가
4. 어떤 조건에서 깨지는가
5. AI에게 준 지시가 실제 코드와 검증에 어떻게 반영됐는가
